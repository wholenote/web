# Brian website design

## Direction

Create a personal collection that is enjoyable to explore: a calm, carefully typeset canvas with tangible cards and brief moments of play. Prioritize Brian's writing, recommendations, photographs, and projects. The shell establishes order; interaction provides character.

Use Balatro for physicality, anticipation, and satisfying resolution. Use Vincent Passaro's site for hierarchy, negative space, and selective motion. Keep Brian's warm cream, plum, berry, mint, and nubcat identity shared by the header and favicon. Brian prefers a plain, lowercase interface with one font and minimal framing; avoid decorative rules or extra controls that make the page feel templated. These are deliberate project adaptations, not claims about either reference's exact design system.

Read [research.md](references/research.md) when interpreting the inspirations, proposing a new visual direction, or explaining their provenance. It records observations from 2026-10-07 and distinguishes them from this project's decisions. Do not require new external research for routine work.

## Design principles

1. **Content leads.** A visitor should understand the page and find its main content before encountering elaborate controls or animation. Give each view a clear heading and a dominant content region. Reserve generous hero space for pages that have something to introduce.
2. **Calm shell, playful objects.** Keep navigation, prose, tables, and long lists steady. Give selectable cards and deliberate reveal actions modest depth, lift, press, and settle. One prominent animated event at a time is the default.
3. **Color has a job.** Cream is reading, berry is primary action, mint is selection or success, and gold is favorites or attention. Pair color with a label, shape, border, or icon. Avoid assigning every panel a different accent.
4. **Texture stays behind content.** A restrained grain or slow color field can add atmosphere. It must not muddy letters, photographs, maps, or focus rings. Avoid blanket CRT distortion, scanline flicker, and effects that move reading text.
5. **Personality comes from real content.** Use accurate notes, places, dates, and counts. Keep copy plain and specific: Brian prefers direct labels over sayings, poetic filler, or “field notes” branding. Match his texting style with lowercase headings, navigation, labels, and prose; use “made by brian” in the shared header, with no name footer or restaurant-hours reminder at the bottom of Food. Present restaurant and city names in lowercase without changing their stored data or filter values. Omit map taglines and decorative photo-game slogans. Do not invent terminal telemetry, credits, achievements, professional history, or scarcity to furnish a theme. Reuse existing identity assets instead of introducing unrelated motifs.
6. **Play is optional.** Reading, browsing photos, and finding restaurants must work without games, sound, pointer hover, or motion. An empty state should honestly explain what is available.

## Visual system

Use `src/styles/global.css` as the shared token source. Preserve existing token names where practical. The following palette is the baseline, not a requirement to keep every current color pairing:

| Token | Value | Role |
| --- | --- | --- |
| `--night` | `#0c0b20` | Main canvas |
| `--night-raised` | `#15142f` | Elevated surface |
| `--night-soft` | `#1d1b3d` | Inset or secondary surface |
| `--ink` | `#f7edcf` | Main text and selected neutral controls |
| `--ink-muted` | `#b8b1a8` | Supporting text |
| `--berry` / `--berry-bright` | `#d23b6a` / `#ff7a9a` | Action accent and decorative emphasis |
| `--mint` | `#75deca` | Selection, links, success |
| `--gold` | `#f5c45b` | Favorites, focus, attention |

Accent backgrounds need their own tested foreground. Primary actions now use `--night` text on `--berry-bright` (about 7.84:1), with a `#ff99b1` hover fill (about 9.63:1). Do not reintroduce cream text on a bright berry gradient. Check new pairings and hover states.

Use DM Sans throughout, matching the shared header: headings, restaurant names, prose, controls, and metadata. Use size and weight for hierarchy instead of switching typefaces or adding italics. Preserve system fallbacks and keep mixed Chinese and Latin text legible.

- Use roughly 16–18px for prose and 14–16px for compact descriptions and controls. Meaningful metadata should normally be at least 12px. These are project readability defaults, not WCAG font-size requirements.
- Keep normal text at least 4.5:1 contrast and qualifying large text at least 3:1. Do not turn meaningful metadata into low-opacity decoration. Measure composed colors, including translucent surfaces and images.
- Use a compact spacing scale such as 4, 8, 12, 16, 24, 32, 48, 64, and 96px. Prefer shared spacing and type tokens when adding styles rather than unrelated per-component values.
- Use the existing 1180px maximum shell as a starting point; give prose a narrower measure, around 60–70 characters. Keep mobile gutters comfortable, usually 16–20px unless the content needs a different fit.
- Fine borders and 8–16px panel radii suit the current site. Pills belong to filters or toggles. Restrict hard offset shadows and small rotations to interactive objects or illustrative card stacks.
- Favor plain lowercase headings and direct copy. Food uses “food places i like” with no italics, numbered eyebrow, or redundant introduction. Omit decorative horizontal rules from the shared header, food toolbar, and filter drawer; use spacing to separate these regions. Keep navigation and state cues consistent between Food, Photos, Resume, and future sections.

## Motion language

Choose motion by purpose. The values below are project starting ranges, not timings measured from Balatro. Reuse the shared `--motion-fast`, `--motion-settle`, and `--ease-settle` CSS tokens; use `src/lib/motion.ts` for scripted motion preferences.

| Event | Starting treatment | Timing | Reduced motion |
| --- | --- | --- | --- |
| Hover/focus emphasis | Border/color change; optional 1–3px lift on a fine pointer | 120–180ms, ease-out | Color/border only |
| Press | 1–2px depression and shorter shadow | 80–120ms | Immediate state change |
| Card selection | Stable selected border/inset marker; optional lift and settle | 180–280ms, `cubic-bezier(.2,.8,.2,1)` | Immediate selection |
| Section entrance | At most 8–14px upward travel with opacity | 300–500ms; stagger 40–70ms, capped around 300ms total delay | Fully visible immediately |
| Deliberate reveal | Brief anticipation, sequential reveal, one small settle | 250–450ms; an optional shuffle may take about 600–1000ms | Resolve immediately without cycling |
| Ambient layer | Low-amplitude transform or static gradient | 16–24s if animated | Static |
| Optional headline accent | One brief decorative scramble over stable accessible text | Finish within about 800ms | Final text immediately |

Entrance and scramble effects are optional. Do not add them just to satisfy resemblance. Do not animate every word, list row, route transition, or repeated hover. Keep actual text available in the server-rendered HTML; decorative glyphs must be hidden from assistive technology. Add pending states only after enhancement initializes successfully.

Prefer `transform` and `opacity`; avoid animating layout, large blurs, or full-page filters. Keep focus and scroll position stable during reveals. Do not delay navigation for decorative transitions. Cancel obsolete timers/frames when the selection changes or the component unmounts. Avoid introducing a motion library solely for a small effect.

Reduced motion must cover CSS **and** JavaScript: scrolling, Leaflet pan/zoom/fly operations, timers that cycle results, and any canvas work. Use immediate scroll and explicit nonanimated map operations. Do not assume a CSS media query disables `scrollIntoView({ behavior: "smooth" })` or third-party animation. Respect preference changes for ongoing effects. Continuous decorative motion should have a pause mechanism or be omitted when it distracts from reading.

## Components and interaction

- **Navigation:** readable labels, visible active state, generous hit areas, and an obvious keyboard focus indicator. Provide a skip link into the main content. Use the same nubcat image for the header and favicon beside lowercase “made by brian,” with both image and caption visible on phones. The current seasonal image is `/favicon-holiday.png`, made from Brian’s supplied Santa-hat nubcat, with an opaque white hat brim and white pom-pom while the exterior background stays transparent; preserve the original `/favicon.png` for switching back. On Food, the home link returns to the top without reloading or visiting the root redirect. Use color and weight for the active nav item without a decorative underline, and omit the sound toggle. Resume is available at `/resume/`. Photos remains temporarily unavailable: show plain “coming soon” text, disable its header entry without a keyboard stop, redirect direct visits to Food, and preserve its source content for reopening. At 760px and below, keep the brand and a single “menu” disclosure in one row. Open Resume, Food, and disabled Photos in an anchored dropdown above page content, without expanding the header or scrolling the page. Expose expanded state; close on Escape, outside click, link activation, or keyboard focus leaving the menu; return focus when a focused link is hidden. Restore inline links above the breakpoint. Keep the full links accessible as the no-JavaScript fallback. Keep narrow headers from overflowing.
- **Resume:** use a white canvas, including the shared header, with dark text and restrained green selection accents. Center a compact, landscape business card with Brian’s name, role, specialties, and contact information. Company names sit within the card’s padding, without plus signs, a separating rule, boxed selection backgrounds, or instructional prose below the card. Use a 300px-tall card on desktop and a 340px-tall card on phones, with the company names pulled up into the identity face. The selected role and three concise bullet points take over the entire card; the pixel wave must also cover and hide the company names. Return the names with the identity face when the pointer leaves. Move keyboard focus to the details when the focused company handle disappears, and restore it to the same handle on Escape or return. Omit cities and months; show years only (2021–present, 2020, 2019). Support hover, keyboard focus, and tap. Moving the pointer off the card into the background animates back to the identity face; leaving the card by keyboard also restores it. Provide an explicit return action for touch and Escape, a full PDF link, and an education/certifications button below the card actions. Spell the degrees in full as “Master of Science in Cybersecurity” and “Bachelor of Science in Computer Science.” Education opens in a centered native modal dialog rather than expanding the page. Keep the enhanced resume page within one dynamic viewport with no document scrolling; let the card shrink on short screens and contain any necessary overflow inside its face or the dialog. Support close, backdrop dismissal, native modal focus containment, Escape, and focus returning to the education button. Preserve an inline disclosure and readable document flow as the no-JavaScript fallback. Reveal the new face through small square cells in an expanding radar wave originating at the selected company name, with a restrained pale-green leading edge. Use about 1.25 seconds to reveal a role and 950ms to restore the identity, reflecting Brian’s explicit preference for a slower pixel transition. Keep card dimensions fixed and text stationary. Cancel and settle interrupted animation frames before a new selection, finish on resize or page exit, and resolve immediately when reduced motion is enabled or changes during a sweep. Keep all experience content server-rendered and readable without JavaScript. Source the professional content from `src/data/resume.ts` and the supplied resume; do not invent roles or achievements.
- **Food:** list favorites first in each city, preserving existing order within each tier and numbering cards in display order. Use a 32px gap below the site header (24px on phones). Explain favorite stars with “one of my favorites.” on hover, focus, or tap, with Escape and outside-click dismissal. Keep cards compact with 12px top padding, 26px titles, an inline order label that inherits the suggestion’s font size, and a 44px Directions target. Show the restaurant name, cuisine, price, neighborhood, and Brian’s suggested order when supplied; omit generic descriptions. Place the Directions link at the bottom-right of each card, using the shared card inset at every breakpoint. Omit the redundant upper card arrow. Use only country flags for cuisine markers; provide restaurant-specific origins for broad categories or mixed cuisines. Keep the native city selector with an inset chevron. Order its cities by total restaurant count, largest first, keeping ties in their existing order and the order stable while filtering. Group the native city selector, all/recommended/favorites buttons, and filters button in one compact toolbar. Omit the exploring label. On phones, put city and filters on the first row and recommendation tiers across the next row. Expand cuisine/price controls inline directly below the toolbar, expose expanded state, show the active filter count, and support Escape returning focus to the filters button. Keep filters collapsed after enhancement initializes, with their contents visible if JavaScript is unavailable. Open Food in “world view” by default and keep it available in the city selector. Server-render the world selection and total recommendation count; keep all restaurant cards accessible as a no-JavaScript fallback. It includes every suggestion regardless of saved city filters, hides the restaurant card list and city-only filters/picker, and uses the full map width on every screen. Group nearby restaurants into numbered markers while zoomed out; activate a group to zoom in, then activate individual restaurant icons for on-map details with name, cuisine, price, location, favorite status, suggested order when supplied, and directions. Keep popups within narrow map widths, support keyboard focus and Escape, and honor reduced motion for map and popup panning. Returning to a city restores its list and existing filters. City browsing starts in List on phones, with an explicit Map toggle; refit Leaflet after revealing a previously hidden map. Synchronize deliberate card and marker selection, not incidental pointer movement. Put the random picker trigger in the existing results row so it never takes a separate collapsed row or panel. Use a small dice icon with “pick randomly” text on desktop, and a 44px icon-only button with an accessible label on phones, beside the list/map toggle. Expand the full picker inline below the results row only on activation, expose expanded state, and support Escape returning focus to the trigger. Its panel has no decorative card framing; it draws from every restaurant in the city, explicitly independent of filters, and reveals cuisine, price, then place. Keep the picker free of explanatory prose and repeated outcome messages; announce the chosen restaurant through the result slot’s live region. Omit the redundant map-selection hint. Keep map labels and attribution readable; a dark map is optional, not a reason to blindly invert tiles or lose geography.
- **Photos:** let the photograph dominate and retain its intended color. Use a simple image frame with a numbered filmstrip, without decorative corner marks or a compass glyph; preserve the full image by default and stack the photo above controls on tablet/phone. Use a daily five-photo country game: select five distinct photos with a date-seeded shuffle, one guess per photo, a final score out of five, and browser-persisted daily progress. Reset at midnight UTC and explain that time in the UI. Lock future rounds and hide their preview images; one correct guess earns one point, an incorrect guess or reveal earns zero. Reveal & browse skips all unfinished rounds. Support loading, missing images, validation errors, reveal, review navigation, completion, and day rollover; never offer a scored same-day restart. Keep location hints out of unrevealed alt text and accessible figure names. Do not fabricate Brian's photographs. The user-authorized demo roll uses credited, locally hosted filler photos, visibly labeled as demos; retain that distinction until replaced by Brian's images.
- **About/projects:** use clear personal information and selected work. Apply the same typography and spacing; card illustrations and factual timelines are optional. Missing content is a content dependency, not permission to invent a biography.
- **Sound:** the site is silent, with no sound toggle or shared audio listeners. Keep visual feedback complete. Do not restore interface sounds or infer sound consent from a saved legacy preference.
- **Inputs and selection:** native semantics first. Give hover behavior a keyboard/touch equivalent; expose persistent selection through appropriate ARIA state. Do not hide the focused control without moving focus to a logical successor. Scope arrow-key shortcuts to the relevant experience and avoid intercepting editing or native-control keys.
- **Responsive layout:** test around 320, 390, 768, and 1440px plus any affected breakpoint. Stack content in useful reading order. Keep primary content reachable before large optional widgets. Prefer 44px control targets for comfort; WCAG 2.2 AA's 24px target-size rule has exceptions and is a separate minimum. Use contained horizontal scrolling only when discoverable and keyboard usable. Check zoom/reflow, long titles, and mixed-language names.

## Working in this repository

Inspect the current pages, shared CSS, and components before editing. Shared framing and metadata live in `src/layouts/SiteLayout.astro`; interaction lives in `src/components/SiteHeader.astro`, `FoodGuide.astro`, and `PhotoGame.astro`. Content data belongs in `src/data/`. The dormant hero/ticker/illustrated-map CSS was removed during the October 2026 refinement; extend rendered components rather than reviving unrelated visual systems.

For implementation requests, make the scoped change, inspect the rendered result at relevant widths, exercise the changed states with keyboard and pointer, and check reduced motion. For functional edits run the appropriate existing tests and Astro checks; documentation-only work does not require adding application tests. Do not publish as a side effect of design work.

For audit requests, inspect the live local pages and source, then report:

- What aligns with the principles and should be retained.
- Specific deviations, location, user impact, and priority.
- A concrete acceptance criterion for each proposed fix.
- Which findings are visually observed, source-derived, or unverified because content/state is unavailable.

An audit is not an instruction to redesign or implement its findings. Do not mark a page aligned solely because its palette matches. Do not claim a motion, performance, accessibility, or photo-state check passed unless it was actually tested. The dated baseline is [docs/design-audit.md](../../docs/design-audit.md).
